# Domain glossary

Status: Release 1 definitions agreed on 2026-10-03. Future-release behavior remains deferred.

| Term | Current meaning | Notes / future decisions |
| --- | --- | --- |
| Architecture | An acyclic graph of Caller Group, Load Balancer, Gateway, Server, and Database components. Cycles and loopbacks are forbidden. | Component roles and validation follow the agreed release contract. |
| Database | A release 1 component representing a database receiving modeled traffic. It uses per-tick capacity/drop accounting and treats handled traffic as terminal completions. | Terminal role; one forwarded request counts as one database request. Query timing is excluded. |
| Cache / caching | Requested for the next release; outside release 1. | Hit/miss behavior, downstream traffic, capacity, state, and metrics. |
| Simulation | A fixed-snapshot calculation using one-hop-per-tick propagation and per-tick capacity/drop accounting. | Implementation defaults are specified in the agreed release contract. |
| Tick | One virtual second. Processing capacity resets per tick; output becomes downstream input next tick. | This boundary applies to source output too. |
| Virtual time | Time within a run, measured in ticks. Configurable total run length defaults to 60, with per-tick reporting and run totals. | Stop at the configured total and report remaining in-flight traffic. |
| Offered traffic / test RPS | Total RPS generated by a caller group, shared across its callers. Earlier questions called this part of the "workload." | Aggregate tick counts approximate evenly spaced arrivals. |
| Caller group / client node | A group generating shared total RPS. 100 callers at 100 group RPS produce 100 total requests per second, averaging one per caller. Source capacity is unused. | Generated output arrives at its first destination next tick. |
| Maximum RPS | A user-supplied per-tick processing capacity. Excess arrivals are dropped. Caller groups do not use capacity limits in release 1. | Yellow at 80% to below 100%; red at 100%. |
| Round-robin | Routing that selects outgoing destinations in rotation. | Persist destination order, retain the cursor across ticks, and reset it for each new simulation. |
| Weighted split | Deterministic routing by configured relative shares, using fixed-order integer remainders each tick. Three requests at 50/50 always allocate 2/1. | Floor normalized shares, then assign the remainder in fixed positive-weight destination order; at least one weight must be positive. |
| Drop | A request is discarded at a processing node when current-tick capacity is exhausted. Routers do not redistribute it. | Included in cumulative conservation accounting. |
| Fanout | A request generates traffic to multiple outgoing destinations. | Deferred for a future phase; the first phase selects one destination per routing decision. |
| Received | Requests available to a processing node during the reported tick, scheduled by upstream output in the previous tick. | Source output also obeys next-tick arrival. |
| Handled / accepted | Received requests admitted within a node's configured capacity; handled = received minus dropped. | Forwarding versus terminal completion depends on node role. |
| Capacity used | Handled requests divided by configured processing capacity for the tick. | Positive integer capacity; yellow at 80% to below 100%, red at 100%. |
| Component / BaseComponent | An element of the architecture with shared capacity configuration and runtime accounting, plus type-specific generation/routing behavior. | Server can terminate or forward through one connection; Database terminates. |
| Simulation result | Output describing modeled architecture behavior; it does not promise real infrastructure capacity. | Metrics, conservation accounting, and acceptance examples follow the release contract. |
| Release | A selected delivery scope. The next release is planned by choosing relevant items from the follow-up backlog. | Scope and criteria for each future release. |
| Release 1 | The local version targeted for October 3–4, 2026; called "first phase" earlier in the interview. | Acceptance examples are recorded in the release contract. |
| Saved architecture | An architecture explicitly saved in SQLite with component configuration and test RPS, retaining its latest saved version. Unsaved changes should trigger a prompt when leaving. | Whole JSON documents plus ID/name/version/timestamps; Duplicate deferred; in-app Save/Discard/Cancel and browser leave/stay warning. |
| Export | A future way to extract an architecture and its configuration; not required for release 1. | File format and import behavior. |
| Tick frame | Aggregate node/connection counts and boundary in-flight counts for one tick. Processing metrics include received/handled/dropped; no individual traces in release 1. | Serialized fields follow the agreed release contract. |
| In flight | Generated requests scheduled for another hop that have not completed or dropped at the recorded boundary. | Reported at the final boundary; no automatic drain ticks. |
| Playback | Replay of aggregate tick frames calculated for a fixed simulation snapshot, with play/pause and fast-forward controls. | Display details and metric labels. |
| Complex system | The kind of simulation for which Python performance might justify considering Go. | Graph size, request count, modeled duration, and acceptable calculation time. |

Latency modeling is deferred for release 1. Capacity use and dropping excess traffic follow the agreed release contract. Queueing and concurrency remain outside release 1.
